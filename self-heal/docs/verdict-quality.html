Beyond flow-passes: what it takes to say "safe to release."

The same three-layer question — did it happen, does it stay coherent, is the underlying number or state actually correct — traced through four different domains. The layering doesn't change; the entities it has to name do. Switch domains below to see what's constant and what isn't.

§3 The minimum ER model to author L2 and L3

You cannot write invariants or oracles without naming the entities they relate. This is the smallest domain schema that lets the case above be asserted end-to-end.

Core entities Derived (never authored, always computed) Rules & assumptions (versioned, sourced)

How each entity earns its keep

  • ComputationRule is the linchpin. Versioned + source-linked, so an oracle's "expected" is defensible instead of asserted. Without it you cannot distinguish a broken app from a stale test.
  • Assumption separated from Rule — inflation and return change more often than the formula does; you want to swap the number without editing the oracle.
  • ComputedGoal is derived, not stored input. Marked dashed to make the boundary explicit — everything on the right of the derivation edge is testable output, not test fixture.
  • Invariant is a first-class row, not code buried in a test file. Enables "which invariants failed on this release" reporting — the actual release-risk indicator.
  • BugClass closes the loop: every escaped bug is tagged with the layer that should have caught it. Over time this tells you where to invest more oracle vs invariant work — the same empirical validation loop you already run for false-heal=0.
  • FieldDataDistribution — turns fuzzing from random to realistic. p5/p50/p95 plus explicit edge cases (S$0, S$99M, 1-year horizon) so property tests explore the space users actually inhabit.

§5 How this connects back to false-heal=0

The gating principle carries over cleanly, in every domain above. A screen-flow test that passes on a mispriced goal, an under-charged cart, a wrong fare, or a phantom EC2 charge is a false-heal at the verdict layer — the framework said "safe" when the app was silently wrong. L2 invariants are the equivalent of your diagnosis pipeline: they cannot always tell you the right answer, but they can refuse to say "safe" when coherence breaks. L3 oracles are your deterministic matcher: expensive to build, defensible when they fire, applied only where being wrong matters.

Same discipline, one layer up: a correct abstain with a named reason — "we cannot verify this charge because no rule is bound to this transaction type" — is a deliverable, not a failure. That is the shape of a release-risk indicator a customer can trust, whether the product is a goal planner, a checkout, a ride, or a cloud console.
