Cross-scenario invariants: the LLM is called exactly once per intake event in every scenario · the delta log is the only source-of-truth writer for spec state · the reducer is the only place that can refuse a delta · Kuzu is only written by the runtime, never by intake · confidence flags (measured / asserted / extracted / proposed / confirmed) flow end-to-end so downstream agents can distinguish design-intent from observed behavior.

03Agentic control loop

A learning/reflection layer sits above the deterministic flow, observing each step and adjusting thresholds, retraining extractors, and escalating to humans. Not one big LLM agent — a small set of scoped observers, each with a defined input signal, quality metric, and action space. LLMs only in observers where genuine judgment helps (extractor accuracy sampling, contradiction triage explanation).

Why not one big LLM agent A monolithic "agent that watches everything" is expensive, non-deterministic, and unauditable. The observer + control split gives you: (i) most observers are cheap and rule-based; (ii) LLMs appear only where they add value (extractor sampling, reflection diagnoses); (iii) every adjustment is a config PR a human signs off, not a runtime mutation. That preserves the false-heal=0 gate — self-learning does not mean self-mutating.

How this maps to the entity map (§02) The chat surface sits above L5 (consumers) in §02 — it's not a new layer; it's a new way to trigger the same intents. Every chat action is one of the existing writes (delta_log, authoring, runtime). No new tools, no new storage, no new trust surface — just a router with a closed intent vocabulary in front of the stack.

Screenshot-repair sub-flow — the highest-leverage healing intent

The moment a user says "this button is broken, here's the screenshot" is the moment the healing pipeline gets a human-confirmed anchor for free. That label is worth more than 100 synthetic drift-torture rows. This sub-flow shows how the intent turns triage into training data.

Why this is worth more than synthetic drift data Drift-torture generates candidate failures; the healing ladder has to guess which candidate is correct. A user pointing at a screenshot removes the guess — the anchor is confirmed at the moment of user friction. One heal_element row is worth 100+ drift-torture rows because it's a real production locator drift, labelled by the human closest to the truth. Feeds directly into the Verdict observer (§3), which is where thresholds and future locator model fine-tunes come from.
Guardrails specific to this intent (i) User must confirm the resolver's element pick before any write — a wrong anchor writes a wrong label forever. (ii) The heal-diff is displayed before commit — false-heal=0 gate still applies even with a human in the loop. (iii) The label is tagged confidence:user_confirmed so downstream models can weight it appropriately. (iv) If the resolver can't find a matching element with reasonable margin, it escalates rather than guessing — the intent falls through to mark_broken.
